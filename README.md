# 急件 · express-media

**视频太大发不出去？按平台限制压好、封好、发出去。**

录完一段 1080p 会议录像 90MB，微信聊天窗口发不出去；传到一半失败；压完画质糊成一团还得再试一次。
市面上的工具要么让你手动调 ffmpeg 参数，要么把你的视频传到别人的服务器上。

急件做三件事：

1. **先告诉你发不发得出去** —— 体检完直接列每个平台的上限、超了多少、这个数字是谁说的
2. **压到刚好能发** —— 压完**真的量体积**，超了就按实测比例推下一档，直到达标或明确说做不到
3. **封成能直接发的成品** —— 顺带出一张投递卡 HTML（封面 + 前后对比 + 各平台判定）

**全部在本机跑，文件不上传任何服务器。** 零第三方依赖，只需要一个 ffmpeg。

---

## 快速开始

```bash
node bin/express.mjs doctor            # 体检环境（先跑这个）
node bin/express.mjs inspect 录屏.mp4   # 多大、多长、能不能发
node bin/express.mjs fit 录屏.mp4 --to wechat-chat
```

装成全局命令：

```bash
npm link          # 之后直接用 express ...
```

## 命令

| 命令 | 干什么 |
| --- | --- |
| `express doctor` | 检查 ffmpeg/ffprobe，并**指出哪些候选是坏的**（见下文「悬空的 ffmpeg」） |
| `express platforms` | 列出各平台上限、来源、置信度 |
| `express inspect <文件...>` | 体检：时长/分辨率/码率/旋转/HDR + 各平台能不能收 |
| `express fit <文件> --to <目标>` | 压到能发（实测收敛） |
| `express split <文件> --to <目标>` | 一个文件实在压不进去，切成几段 |
| `express trim <文件> --start 0:10 --end 1:20` | 裁一段 |
| `express gif <文件> --width 320 --square` | 转 GIF / 表情包 |
| `express card <文件> --from 原始文件` | 生成投递卡 HTML |
| `express ledger` | 压缩台账与节省报告 |

### `fit` 的参数

| 参数 | 说明 |
| --- | --- |
| `--to <目标>` | 平台 id（`wechat-chat` / `telegram-bot` / `discord-free` / `gmail` / `xiaohongshu` / `douyin` / `bilibili` / `shipinhao` …）或自定义大小（`25MB` / `500k` / `1.5g`） |
| `--preset <档>` | `keep` 保画质（不降分辨率）｜ `balanced` 默认 ｜ `small` 再小一档 |
| `--out <路径>` | 输出文件，默认在原文件旁边加后缀 |
| `--speed <档>` | `ultrafast`…`veryslow`，默认 `medium` |
| `--max-passes <n>` | 最多试几档，默认 4 |
| `--dry-run` | 只出计划不真压（**不产生任何文件**）；预估给的是区间，因为不同内容的压缩难度能差几倍 |
| `--normalize` | 体积已达标也重编码一遍（把方向烤进像素、统一容器） |
| `--card` | 压完顺手生成投递卡 |
| `--no-ledger` | 不记台账 |

退出码：`0` 达标 ｜ `1` 压了但仍超限 ｜ `2` 参数/环境问题。脚本里可以直接靠它判断成败。

### 其他命令的参数

| 命令 | 参数 |
| --- | --- |
| `split` | `--parts <n>` 段数（不给就按「体积 ÷ 目标」自动算，给 1 会抬到 2）｜ `--out <目录>` 输出目录 |
| `trim` | `--start` / `--end` / `--duration`（`1:30`、`90`、`01:02:03` 都认）｜ `--fast` 不重编码（切点不精确，但快） |
| `gif` | `--width <px>` ｜ `--fps <n>` ｜ `--start` / `--duration` ｜ `--square` 裁成正方形（不拉伸） |
| `card` | `--from <原始文件>` 把压缩前后的体积对比写进卡片 ｜ `--out <路径>` |
| `ledger` | `--out <报告.html>` ｜ `--json` |

## 它凭什么比「自己敲 ffmpeg」强

### 1. 不量就别说成功

大部分压缩脚本是「跑一次 ffmpeg，拿到就交」。急件每压一档都用 `ffprobe` 量真实体积，
按**实测超出倍数**（体积对 CRF 近似指数关系，所以按 `log2` 推）算出下一档。
90MB → 微信 25MB 通常 2–3 档内收敛。

### 2. 压不进去就说压不进去

压到最低分辨率、CRF 拉满还超限时，它不会闷声交一个 38MB 的文件，然后说「好了」。
它会：

```
✘ 还是超了 13.2 MB
  换个思路：
    · 裁到约 22 秒（现在 25 秒）大概能压进去
    · 按 4 段分开发，每段都小于上限
    · 上传到网盘 / 视频平台后发链接，这类场景大多数平台都收链接不收文件
```

「裁到多少秒」是按最低档的实测密度反推的，不是随口说的。

### 3. 内容判定是量出来的，不是猜的

同一个分辨率、同样帧率，屏保录屏和游戏实录需要的码率能差 3 倍。
急件会真的解码抽样帧，统计**变化像素占比**和**细节密度**，再据此选压缩档位：

| 判定 | 实测 motion | 起始 CRF | 上限 CRF |
| --- | --- | --- | --- |
| 静止 / 文字（录屏、PPT、聊天记录） | 0.0002 | 28 | 36 |
| 一般画面（实拍、人物讲话） | 0.06 ~ 0.12 | 25 | 30 |
| 高运动（游戏、体育、快速摇摄） | 0.19 ~ 0.31 | 23 | 28 |

阈值不是拍脑袋定的，是对 10 段合成素材量出来的（`npm run calibrate` 可以复现），
两个分界都落在实测分布的明显空档里。

### 4. 竖屏不会躺着发出去

手机拍的竖屏视频，很多播放器不认 `display matrix`，发出去是躺着的。
急件把方向**烤进像素**，并且显式删掉容器里的显示矩阵 —— 只做 `transpose` 是不够的，
实测 ffmpeg 会把输入的矩阵一路带到输出，结果播放器再转一次。

体积已经达标的时候，它**不会**为了统一而白白重压一遍（那是在拿画质换一个不存在的问题），
但会提醒你这件事，并给一个真能解决它的开关：

```bash
express fit 竖屏.mp4 --to 8MB
# ! 这个文件靠旋转元数据（90°）摆正，体积达标所以保持了原样、没有重编码。
#   个别客户端不认这个元数据，收到会横着显示。真遇到了就加 --normalize 强制把方向烤进像素。

express fit 竖屏.mp4 --to 8MB --normalize   # 真要烤进像素
```

### 5. 格式不吃香，体积够也没用

HEVC、MKV 这类文件体积达标照样发不出去（微信、Discord 内联播放器都挑）。
体积达标但编码不是 H.264 时，急件照样重编码。

## 平台限制表带来源，也带「这条有多可信」

各平台限制又变又矛盾：Discord 免费版 2026-08-17 从 10MB 提到 20MB，部分账号 A/B 到 25MB；
微信有「社区实测 25MB」和「厂商客服 1GB」两套说法。

所以每条限制都带 `confidence`：

- `official` —— 官方文档或厂商客服明确写出
- `community` —— 社区实测或第三方汇总，可能已过期
- `mixed` —— 存在互相矛盾的口径，**两种说法都列在 `variants` 里**，取更保守的作为上限

```bash
express platforms        # 看全表和来源
express platforms --json # 拿去喂脚本
```

表在 `data/platforms.json`，改完记得改 `updatedAt`（有测试盯着这个日期不能是未来）。

## 悬空的 ffmpeg

Windows 上 `winget upgrade` 之后，`%LOCALAPPDATA%\Microsoft\WinGet\Links\ffmpeg.exe` 可能变成**悬空符号链接**：
`where ffmpeg` 查得到、`Get-Command ffmpeg` 解析得出路径，一执行就报「系统找不到指定的文件」。

只判断「路径能不能解析」是不够的，**必须真的执行一次**。所以：

- `express doctor` 会把所有候选都跑一遍，把坏的单独列出来，还告诉你为什么坏
- 发现好用的 ffmpeg 之前不会放弃，也会去翻已知安装位置（`~/.minimax/tools/ffmpeg/*/bin`、scoop、`C:\ffmpeg\bin` 等）
- 紧急情况可以 `EXPRESS_FFMPEG=/path/to/ffmpeg` 指定

```bash
express doctor
# ✔ 可用：C:\Users\...\ffmpeg-9.0.2-essentials_build\bin\ffmpeg.exe
# ! 这个 ffmpeg 用不了：C:\...\WinGet\Links\ffmpeg.exe
#   路径能解析，但执行时找不到目标文件——典型的悬空符号链接（来源：PATH）
```

## 仓库 与 MiniMax Code 插件

同一份代码有两种装法，用途不同：

| | 仓库（本目录） | 插件 |
| --- | --- | --- |
| 位置 | 本仓库根目录 | 插件安装目录（如 `<插件目录>`） |
| 装了什么 | 全部：源码 + 测试 + 开发脚本 | 只装运行时：`bin/` `src/` `data/` + 一份 Skill |
| 合成素材 | 有（101MB，已 gitignore） | **没有** —— 太大，插件不带 |
| 用途 | 改代码、跑测试、标定阈值 | 在 Mavis 里说人话就能用 |

**没打包的东西影响功能吗？不影响。** `test/`、`scripts/`、素材都只是开发和验证用的，
运行时代码一行都没引用它们。
9 个命令逐个实跑过，产出物都用 ffprobe 独立解过。

**但插件里的代码是拷贝，不是链接。** 改完仓库要同步过去，否则两边会分叉：

```powershell
Copy-Item <仓库根目录>\src\*.js      <插件目录>\src\ -Force
Copy-Item <仓库根目录>\data\platforms.json <插件目录>\data\ -Force
```

改完同步之后，**别只跑测试**——测试验的是仓库那份。至少拿插件里的那份实跑一次：

```powershell
node <插件目录>\bin\express.mjs doctor
node <插件目录>\bin\express.mjs split <你的视频> --to 10MB --parts 4
```

然后量一下每段的实际时长加起来对不对得上原片。
这一步不是多余的——`split` 的裁剪曾经坏着（每段都输出完整原片），
而仓库里 6 个测试全绿，因为它们只验了「体积达标」和「时间范围元数据自洽」。

## 验证

这个项目的检查是**真的会红**的，不是摆设。

```bash
npm run fixtures     # 合成 10 段测试素材（录屏/摇摄/高运动/竖屏旋转/黑边/大文件…）
npm run test:unit    # 91 个单测，约 5 秒
npm run test:e2e     # 60 个端到端：真跑 ffmpeg，ffprobe 量产物，约 4 分钟
npm run calibrate    # 打印内容判定阈值用的原始数据
npm run mutation     # 变异测试：故意改坏产品，看检查会不会红
```

几个刻意设计的点：

- **夹具必须自证**。每个素材声明自己必须具备的性质（竖屏真的带 90° 旋转矩阵、letterbox 只有左右黑边、silent 真的没音轨），
  不符就报错。原因：`-metadata rotate=90` 在 ffmpeg 9 上不生效，造出过「看着正常、其实没旋转」的假夹具，
  它不会让测试失败，只会让测试**变得没有意义**。
  素材目录里还多了一道检查：**只允许出现配方产物**。真实事故是验证投递卡时忘了给封面指定路径，
  抽出来的 `motion.cover.jpg` 就落在了素材目录里——而那是**输入**目录。
- **源码不许带 UTF-8 BOM**。用 PowerShell 5.1 的 `Set-Content -Encoding UTF8` 改文件会偷偷写上 BOM，
  一次就污染了 22 个文件（包括插件要用的 `src/*.js`）。要改文件用编辑工具，或
  `[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($false)))`。
  有测试盯着——而且它第一次运行就抓到了写它自己的那个文件。
- **测试跑完不留垃圾**。临时目录用 `after()` 钩子清理（不是 `exit` 事件：刚被 ffmpeg 写完的视频在 Windows 上还锁着，
  挂在 exit 上删不掉，而失败又被 `catch` 掉——「不留垃圾」就是这样悄悄失效的）。清理失败会发 warning，不静默吞。
  这条曾经失效过一次，代价是 353MB 的临时目录。
- **判定必须与磁盘一致**。每个端到端用例都拿 `statSync` 量真实体积，
  断言「工具说达标 ⇒ 文件真的达标」「工具说超限 ⇒ 文件真的超限且给了替代方案」。
- **变异测试**。17 处定向破坏（旋转只读老式 tag、达标判定改用估算、阈值写反、裁剪 `-ss` 位置搞错、
  投递卡不转义、`--dry-run` 落文件……），每一处都必须被抓到。抓不到就说明那条检查形同虚设。
  **这条工具自己也配了反向对照**：一个只改注释、行为不变的「无效变异」必须报「没抓到」。
  没有这条对照，校验器自己撒谎都没人知道（开发过程中它确实撒过一次谎：极性写反，
  于是每个被改坏的变异都报成「没抓到」，而实得值其实全在说「它坏了」）。
- **模糊测试**。40 组随机「素材 × 目标体积 × 档位」，不预设「应该成功」，
  只钉一条铁律：要么真达标，要么明确报做不到，**绝不出现「报告与实物不符」**。
- **本地化守卫**。界面承诺是中文，所以扫输出里有没有整句英文。
  判据是**按词数**而不是「有没有非 ASCII 字符」—— 纯 ASCII 的 `output_path is required` 会从后者里完整穿过去。
  而且这个守卫自己也要先证明它量得出东西（见测试里那条「先证明尺子有效」）。

### 迭代过程中被这些检查抓出来的真 bug

不是写完就对的，下面每一条都是先有症状、再定位到根因的：

| 症状 | 真正的原因 |
| --- | --- |
| 转 GIF 报 `No option name near 'bayer'` | 带显式输入标签的滤镜，选项前要用 `=` 而不是 `:`，否则 `:dither` 被当成下一个滤镜 |
| 竖屏压完发出去还是躺着 | `transpose` 只改了像素，容器的 display matrix 被原样带到了输出 |
| 输出目录不存在时所有编码都失败 | 中间临时文件写在编码前，目录却在收尾时才建 |
| 录屏素材被误判成「静止画面」 | 采样降到 64×36，均值化把文字边缘抹平了；改成按原始像素采样 |
| 「裁到多少秒能进去」永远算不出来 | `safeAim` 的固定 512KB 余量把 400KB 的目标吃成了 1KB |
| `--dry-run` 报「压不进去」 | 拿没跑过的实验当结论 |
| 目标填 `0` 时老实压三档再报超限 | 荒唐输入没在入口拦下，浪费几分钟还让人以为自己哪里没设置对 |
| 素材「已存在就跳过」结果跳过了 9MB 垃圾 | 悬空中断留下的截断 mp4 能过 `stat`；改成让 ffprobe 真解一次 |
| 投递卡对「体积够但时长超」的平台显示「超 0 B」 | 判定只按体积算差值，没有区分体积超和时长超 |
| `--out myclip` 撞上 ffmpeg 的 `Unable to choose an output format` | 用户只是没写扩展名，不该由他翻译 ffmpeg 的报错 |
| 平台表格在终端里列对不齐 | 中文是双宽字符，用 `padEnd` 按字符数补必然错位；改成按显示宽度补 |
| 变异测试一度 17 条全绿 | 检查的极性写反了（`caught` 应表示「不变量被违反」），还叠了两个假通过源 |
| **分段的第一段输出完整原片，后面的段内容重复** | 为了「避免 O(N²) 解码」把 `-ss`/`-t` 换成了 `trim` 滤镜，而 ffmpeg 9 上那个滤镜**根本不裁剪**。测试全绿是因为只验了元数据自洽。**性能重构后要逐项对旧行为** |

关于那条 `--dry-run` 的预估：对合成素材标定下来，**一般画面档的模型值 0.050 / 实测 0.0504，几乎正中**；
但「静止/文字」和「高运动」两档的合成素材不具代表性（一个纯色暗背景、一个纯色方块，都比真实内容好压一个量级），
所以**没有**拿它们去反推模型——那只会让模型对真实内容更不准。
代价是预估在跨内容类型时会偏乐观 35% 左右，所以展示的是**区间**而不是单点。

## 边界与已知不足

- 动画和字幕轨不涉及（这里只处理视频文件本身）
- 平台限制会过期，`confidence` 和 `updatedAt` 就是给这件事的
- HDR 内容会被转成 SDR 色调（`--to` 场景里这通常正是想要的，但确实是有损的）
- 批量处理目前一次一个文件；`split` 每次处理一个源文件，没有递归目录
- 目标体积下限是 16KB：再小就不是视频了，与其压出垃圾不如在入口报错
